## 三、分模块测试方式（推荐）

**核心思路：把每个模块做成"能单独跑起来的最小单元"，再去合成。**

| 阶段 | 做法 | 好处 |
|---|---|---|
| 模块开发期 | 独立脚本 / 独立节点 / 独立 launch，参数从命令行传 | 不用起整条任务链；改完立刻能验；崩了不影响别的模块 |
| 模块联调期 | 用 `rostopic` / `rqt_graph` 看接口契约 | 先把"输入输出"定死，再谈实现 |
| 主任务合成期 | 把同一份代码**以库的方式**加载进主任务进程 | 同步、可靠、无超时 |

**每个模块的测试入口建议**（沿用现有约定）：

```bash
# 行为识别（已完成，作为模板）
roslaunch wpb_task1_owner_search qwen_action_recognition.launch \
  auto_repeat_seconds:=5.0 overlay_hold_seconds:=5.0

# 其余模块照此模式，各做一个独立 launch / 脚本
#   机械臂原语：      独立节点 + 手动发一组 lift/gripper 目标
#   垃圾发现：        独立节点，订阅点云，把 objects_3d 结果播报出来
#   多主人区分：      独立节点，喂图片，看输出是谁
```

## 四、主任务合成策略：节点 vs 库

### 结论

**"把圈2 封装成独立节点"本身不是错，但它不是合成手段，而是测试手段。**

| 用法 | 形态 | 适用阶段 | 特点 |
|---|---|---|---|
| **当库用**（`importlib` 加载同一文件） | 同进程函数调用 | **主任务合成 / 正式比赛** | 同步、可靠、无超时、无进程管理 |
| **当节点用**（独立进程 + 话题通信） | 跨进程触发/等结果 | **分模块测试 / 单独调参** | 可单独重启、单独调参，但引入超时与并发问题 |

两种用法的**算法代码是同一个文件**，所以不存在"两份实现"的问题。

### 建议做法

1. **测试期**：每个模块都按"独立节点 + 独立 launch"来做——这正是圈2 的价值。
2. **合成期**：主任务用 `importlib` 直接加载同一份代码，走同进程调用；
   独立节点保留，随时用来复现问题、单独调参。
3. 代码里已经提供切换开关（`action_external_node`，默认 false）：
   - `false`（推荐，正式比赛用）= 同进程库调用
   - `true` = 调独立节点，失败自动回退

### 为什么不建议正式比赛走"节点调用"

- 跨进程意味着可能超时、可能对方没起来、可能忙——都需要额外容错；
- 比赛现场最怕"多一个可能失败的环节"；
- 库调用没有这些风险，而代码复用度完全一样。

## 五、建议节奏

```
第一步（P0，本周）
  M1 播报规范层  +  M2 机械臂动作原语  +  M11 资格认证材料（有截止线）

第二步（P1，可并行）
  M6 地图与航点（需实地采集，越早越好）
  M3 开关对位 / M4 摔倒扶起 / M5 挥手对话（三个交互场景，靠 M2）
  M10 多主人区分（主人注册可后置，区分先做）

第三步（P2/P3）
  M7 找垃圾 → M8 抓取 → M9 入桶（300 分，依赖 M2 与 M6）

第四步
  主任务合成 + 全流程彩排（含入场、离场、异常处理）
```

### 风险提示

- **M9 入桶**风险最高（打翻即清零），一定放最后并留足练习时间。
- **M6 地图航点**是所有"走到主人面前/垃圾桶"的前置，必须尽早实地采集。
- **M11 资格认证**不提交就没有参赛资格，与技术进度无关，别拖到最后。
