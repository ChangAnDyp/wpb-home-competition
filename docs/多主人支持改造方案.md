# 多主人支持改造方案评估

评估日期：2026-09-28
评估对象：`~/catkin_ws/src/wpb_task1_owner_search/scripts/task1_find_owner_real.py`

---

## 一、需求：规则到底要什么

规则原文（2026 居家生活机器人）：

> 现场随机指定 3 位志愿者作为主人……机器人自主进场后，可依次让 3 个主人走到其面前，
> 通过非接触自行交互方式识别主人的特征，并记住主人的名字。

> 每个房间活动的人员数量为 1，主人在各房间中的位置随机。

评分：

| 项 | 分值 | 判据 |
|---|---|---|
| 区分出每个主人 | 3 x 50 = **150** | **以语音播报主人名字为主要依据** |

由此推出三个硬性能力要求：

1. **能同时记住 3 个人的身份和名字**（不是 1 个）
2. **能识别出眼前这个人属于其中哪一位**，并播报**对应的**名字
3. **能拒绝非主人** —— 4 个房间各 1 人，其中 3 位是主人，
   另一个可能是"客人"；若把客人认成主人，这项拿不到分

同一批主人的行为判定（3 x 30）和交互（3 x 50）也依赖"先认出这是谁"。
所以这 150 分实际牵动后面 240 分。

## 二、现状：当前实现只支持 1 个主人

### 直接证据

| 位置 | 代码 | 问题 |
|---|---|---|
| 809 行 | `self.owner_name = ""` | 名字是**单个字符串** |
| 812 行 | `self.owner_face_embedding = None` | 单个平均人脸特征 |
| 813 行 | `self.owner_face_embeddings = []` | 一个**扁平列表**，混放同一个人的所有照片 |
| 5005 行 | `best_owner_face_match()` 在扁平列表里取最大相似度 | 只能回答"像不像主人"，答不出"是哪个主人" |
| 6014 行 | `self.say("我已经识别到主人%s。" % self.owner_name)` | 只会播报**同一个名字** |

### 现有流程

```
run()
  wait_for_hardware_inputs()
  enroll_owner()                 <- 只注册 1 人（问名字 / 确认 / 采脸 5s）
  init_action_recognizer()
  for waypoint in [living_room, kitchen, bedroom, canteen]:
      run_owner_task_at_waypoint(waypoint)
          navigate_to_waypoint()
          scan_for_owner()       <- 比对结果只有"是/不是"二元判断
          say("我已经识别到主人%s" % owner_name)   <- 永远是同一个名字
          recognize_owner_action()
          接近 + 机械臂 / 开关语音交互
```

**结论：任务编排（4 房间巡游、动作识别、机械臂、开关交互）都是完整可用的，
只有"身份层"是单人设计。** 这是改造的有利条件。

## 三、两条改造路线对比

### 路线 A：扩展 `task1_find_owner_real.py`（推荐）

保留它完整的比赛流程，只把身份层从单人改成多人。

**优点**

- 比赛逻辑（4 航点巡游、动作识别、机械臂、开关交互、离场）已经写好并调试过
- 改动集中在身份层，不碰编排层

**缺点**

- 需要小心改 `verify_candidate_with_face`（140 行，含多区域 / 旋转 / 增强回退逻辑）

### 路线 B：扩展 `owner_voice_reid_test.py`

这个文件（2064 行）**已经支持多主人**：`owner_count` 默认 3、
`owner_profile_1/2/3.npz`、`score_owner_match()` 按人打分、
`announce_owner_result()` 播报对应名字。

**它缺的东西**（逐个统计过）：

| 能力 | 现状 |
|---|---|
| 多主人注册 + 识别 | 有 |
| 导航 | 只有**单个航点**（`waypoint_name`），没有 4 房间循环 |
| 动作识别（Qwen 视觉） | 有 |
| 机械臂控制 `mani_ctrl` | **0 处** |
| 电器开关语音交互 | **0 处** |
| 摔倒扶起 | 无 |
| 离场 | 无 |

要补齐这些，等于把 `task1_find_owner_real.py` 的编排层再移植一遍。

### 结论

**走路线 A。** 路线 B 看似"多主人已经现成"，但它缺的是**更复杂、更贴近比赛评分**的
那部分（机械臂、开关交互、4 房间循环），补齐代价比 A 大。

## 四、路线 A 的具体改造清单

### 4.1 数据结构（第 808-813 行）

```python
# 现在
self.owner_reference_images = []
self.owner_name = ""
self.owner_face_embedding = None
self.owner_face_embeddings = []

# 改成
self.owners = []          # 列表，每人一项
#   [{"index": 1, "name": "张三",
#     "face_embeddings": [{"path": "...", "embedding": np.ndarray}, ...],
#     "mean_embedding": np.ndarray},
#    ...]
self.found_owner_indexes = set()   # 已处理过的主人，避免重复计分
```

`owner_name` / `owner_face_embeddings` 建议**保留为兼容别名**（指向当前正在处理的那位），
这样原本引用它们的 9-10 处代码不用全部改。

### 4.2 参考数据来源（第 1288-1330 行 `init_face_recognizer`）

现在把 `data/owner/` 下**所有**图片当成一个人。多人需要分组，两种方案：

| 方案 | 做法 | 评价 |
|---|---|---|
| 子目录分组 | `data/owner/owner1/*.jpg`、`owner2/`、`owner3/` | 简单直观，但要改 `load_owner_images()` |
| **复用注册档案**（推荐） | 读 `data/reid_owner_voice/owner_profile_N.npz` + `.json` | 名字和特征**都已经在里面**，注册工具现成 |

推荐第二种，因为 `owner_voice_reid_test.py` 保存的 json 里**已经写了**：

```json
{ "owner_index": 1, "owner_name": "张三", "has_face_embedding": true, ... }
```

也就是说"注册 -> 落盘 -> 带名字读取"这条链路已经存在，只是任务节点没用它。

### 4.3 匹配层：从"像不像"改成"是哪个"

| 函数 | 行号 | 现在 | 改成 |
|---|---|---|---|
| `best_owner_face_match` | 5005 | 返回 `(最高相似度, 参考图路径)` | 返回 `(相似度, owner_index, owner_name)`，并**同时给出第二名分数** |
| `verify_candidate_with_face` | 5025（约 140 行） | 返回 `(True/False, 分数, 理由)` | 命中时把身份挂到候选上：`candidate["owner_index"]`、`candidate["owner_name"]` |
| `verify_candidate` | 约 5060 | 传递布尔结果 | 透传身份字段 |
| `verify_candidate_pool` | 约 5280 | 返回 `(candidate, yaw)` | 同上，身份随 candidate 走 |

**关键改动：引入"领先幅度"判据**

现在只有绝对阈值 `face_accept_threshold: 0.45`（1 对 1 验证）。
多人识别必须再加一条：**第一名必须比第二名高出一定幅度**，否则判 unknown。

```
if score_best < accept_threshold:            -> 不是任何主人
elif score_best - score_second < margin:     -> 分不清是哪位，判 unknown
else:                                        -> 认定为 owner_index
```

这一条是**防止把 A 认成 B** 的核心，不加上会大量误报。

### 4.4 注册流程（第 1150-1200 行 `enroll_owner`）

改成循环 N 次：

```
for i in 1..N:
    say("请第 i 位主人站到我面前，并说出您的名字。")
    name = wait_for_owner_name()
    say("您说的是%s，请确认。" % name)
    capture_owner_face_embeddings()      # 复用现有函数，不用改
    owners.append({"index": i, "name": name, ...})
```

新增参数：`owner_count`（默认 3）。

### 4.5 播报与去重（第 5994-6030 行）

```python
# 现在
self.say("我已经识别到主人%s。" % self.owner_name)

# 改成
matched_index = owner_candidate.get("owner_index")
matched_name  = owner_candidate.get("owner_name", "主人")
self.found_owner_indexes.add(matched_index)
self.say("我已经识别到主人%s。" % matched_name)
```

另外建议：若 `matched_index` 已在 `found_owner_indexes` 里（同一位主人被重复识别），
要么跳过动作流程，要么至少不重复计分。

### 4.6 可选增强：接入 ReID

当前任务节点**只用 InsightFace 人脸**，没有任何 torchreid 集成。
躺姿 / 侧身 / 背对时脸可能完全看不到，识别会失败 —— 而这恰恰是规则里
"躺着的主人"那一档。

`owner_voice_reid_test.py` 已有现成的 `score_owner_match()`（人脸 + ReID + 外观三路加权），
可以把它作为**辅助判据**接进来：人脸拿不到时用 ReID 兜底，两者都有时加权。

建议作为第二阶段，先把"多人身份"跑通再加。

## 五、工作量与风险

### 工作量估算

| 阶段 | 内容 | 预估 |
|---|---|---|
| 1 | 数据结构改造 + 兼容别名 | 0.5 天 |
| 2 | 从注册档案读取多人参考（复用现成 json/npz） | 0.5 天 |
| 3 | 匹配层改造 + 领先幅度判据 | 1 天 |
| 4 | 注册流程循环化 | 0.5 天 |
| 5 | 播报与去重 | 0.5 天 |
| 6 | 真机调试 + 阈值标定 | **1-2 天**（最耗时，需真人配合） |
| | **合计** | **约 4-5 天** |

### 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **阈值必须重新标定** | 单人时是"是不是主人"；多人时变成"三位中的哪一位"，原 0.45 / 0.70 都不适用 | 现场用真人采集数据标定，"领先幅度"设为可调参数 |
| **误接受概率上升** | 主人从 1 个变 3 个，误匹配机会变 3 倍 | 加"领先幅度"判据；客人所在房间宁可不认 |
| **触碰已跑通代码** | `verify_candidate_with_face` 140 行，含多区域 / 旋转 / CLAHE 回退，改坏会整体失效 | 保留兼容别名；改完先跑单人回归 |
| **回归验证依赖真机** | 没有人脸数据无法验证准确率 | 提前用真人采集一批照片做离线回归 |

## 六、备选与分阶段策略

### 备选 1：语音问名字兜底（不推荐）

不改造识别，而是每个航点先问"请问您是哪位主人？"再按答案播报。

**问题**：规则要求"通过非接触自行交互方式识别主人的特征"，
靠人自报姓名并非"识别特征"，裁判可能不认；现场嘈杂、ASR 出错就直接丢分。

### 备选 2：先拿稳分，再攻这 150 分（推荐作为节奏安排）

现在已经具备、且**不依赖认出是谁**的能力：

| 项目 | 分值 |
|---|---|
| 自主进场 | 10 |
| 动作判定 | 90 |
| 人机交互 | 150 |
| 自主离场 | 10 |
| **小计** | **260** |

建议节奏：

1. **先**把这条 260 分主线在真机上跑通（当前最大的确定性收益）
2. **再**做多主人改造攻 150 分
3. 垃圾拾取 300 分单独排期

### 备选 3：只做 2 人？不行

规则固定 3 位主人，无法规避。

## 七、结论与建议

1. **值得做**：150 分是单项最高分值，且牵动后续 240 分的稳定性。
2. **走路线 A**：扩展 `task1_find_owner_real.py`，不要换用 `owner_voice_reid_test.py`
   （它缺的是更贵的部分）。
3. **改造面可控**：影响约 35-40 处引用、4 个核心函数，其中只有
   `verify_candidate_with_face`（140 行）需要谨慎对待。
4. **最大技术风险是阈值标定**，不是代码复杂度，必须预留真人调试时间。
5. **建议节奏**：先跑通"不依赖身份"的 260 分主线，再做多主人改造。
